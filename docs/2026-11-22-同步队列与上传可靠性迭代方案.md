## 1. 目标与范围

本轮迭代有且只有两条主线，任何一项改动都必须能回答"它服务哪条主线、解决谁的什么痛点"。

### 主线 A：文件同步正确性

让"该同步的文件一定同步成功、不该判失败的绝不判失败、失败了一定看得见并且能自动收敛"。

成功标准：

1. 服务端收尾元数据异常（缺 `size`、`rangeList` 有洞）不再把成功的上传判成失败。
2. 可恢复错误（超时、5xx、网络抖动）不再在 30 秒内直接终态失败。
3. 失败一定落到 `sync_items`，在文件视图与传输队列都能看到，不再"消失"。
4. 单次同步周期不被单个大文件拖住数十分钟，恢复/核验不再被饿死。
5. 消灭已知的整机死锁路径。

### 主线 B：交互体验

让"每一次点击都有即时、可预期、可撤销的反馈"，核心是**任何用户操作都不应该因为'另一个操作正在执行'而被拒绝或被禁用**。

成功标准：

1. 任何入口点击都有即时反馈，不出现"点了没反应"。
2. 队列类操作（目录对齐、重试、批量操作）一律"先入队、后执行"，UI 从不等待执行完成。
3. 用户在同一屏内可以连续触发多个操作，互不影响。
4. 批量场景有一键入口（重试全部、批量下载、批量释放空间）。
5. 错误文案区分"已排队"与"真失败"，不再出现"同步失败：已加入传输队列"这类自相矛盾提示。

### 交叉点：统一任务队列

两条主线在同一个基座上收敛：**所有写操作先落库为任务（Pending），再由统一调度器按并发槽执行**。这样"点击必有响应"（主线 B）与"长任务不饿死引擎"（主线 A）同时成立。

## 3. 主线 A：同步正确性方案

### A1. 收尾可靠性（C1–C4，Phase 1）

**C1 收尾缺 `size` 容忍**

`src/drive/models.rs:138` 把缺失的 `size` 静默回退成 `0`，`complete_upload_file` 再要求 `0 == 1_075_470_863`，把成功判成歧义。

```rust
/// 收尾响应是否显式声明了 size。缺失与显式 0 必须区分。
pub(super) fn declares_size(body: &Value) -> bool {
    body.get("size").is_some_and(|value| !value.is_null())
}

/// 仅在文件身份、长度及可选名称完整匹配时接受最终结果。
/// size 缺失时按 id + name 接受，并用本地已发送长度补全；显式 size 不一致仍拒绝。
pub(super) fn complete_upload_file(
    body: &Value,
    expected_size: u64,
    expected_name: Option<&str>,
) -> Option<DriveFile> {
    let mut file = DriveFile::from_json(body)?;
    let name_matches = !file.name.trim().is_empty()
        && expected_name.is_none_or(|expected| file.name.as_str() == expected);
    // 身份不完整时一律拒绝：无法证明这次写入属于本任务。
    if file.id.trim().is_empty() || !name_matches {
        return None;
    }
    if declares_size(body) {
        // 服务端明确给出长度就必须与本地一致，0 字节也不能放过。
        if file.size < 0 || file.size as u64 != expected_size {
            return None;
        }
    } else {
        // 未回填长度：按任务快照补全，避免结算层把 0 当成真实长度。
        tracing::warn!(id = %file.id, expected_size, "收尾响应未回填 size，按本地快照补全");
        file.size = expected_size as i64;
    }
    Some(file)
}
```

安全性来自"只容忍字段缺失，不容忍显式 0"。

**C2 收尾元数据未就绪 → 轮询**

`query_session_status` 在 2xx 但对象不完整时返回"待收尾"，让 `upload_resume_session` 的 `FINAL_STATUS_MAX_POLLS` 真正生效：

```rust
        // 已有对象身份但元数据未回填：交给上层继续轮询，不要立刻判歧义。
        if has_object_identity(&body) {
            tracing::warn!(total_size, body = %body, "上传收尾元数据未就绪，继续轮询同一会话");
            return Ok(ChunkResult {
                uploaded: total_size,
                is_final: false,
                final_file: None,
                process_time_ms: body.get("processTime").and_then(Value::as_u64),
            });
        }
```

轮询窗口：`FINAL_STATUS_MAX_POLLS` 5 → 10，间隔 3s → 5s（约 50 秒）。

**C3 `rangeList` 空洞**

解析结果从单一偏移改为"连续前缀 + 首个空洞"：

```rust
/// 已接收范围解析结果：连续前缀末端 + 首个空洞起点。
pub(super) struct ConfirmedRanges {
    /// 从 0 起连续确认到的偏移；空洞之后的字节不计入。
    pub prefix: u64,
    /// 服务端报告的首个空洞起点；无空洞时为 None。
    pub gap: Option<u64>,
}
```

- 有洞时回退到 `prefix` 重发（只补 17～64MB，而不是整份重传）。
- 连续 3 次无进展 → `AppError::drive_upload_session_expired`，由任务层 `transition_clearing_upload_session` 清会话重建。
- 重叠/倒序仍然按协议错误处理，不放宽。

**C4 分片 4xx 落响应体**：`upload_response_error` 记录 `status / session_sensitive / body（截断 1KB）`，403 按 `error_code` 细分 quota / risk / permission，**暂不改终态策略**（避免死循环）。

### A2. 执行并发（Phase 2）

1. **稳定性检查去全局锁**：`StabilityChecker` 只保护 `tracking` 表，3 秒窗口在锁外等待；同一路径的重复检查做 in-flight 去重。目标：`concurrency=6` 时 6 个上传前置校验真正并行。
2. **规划与执行分离**：planner 产生的传输动作改为"入队 + 后台执行"，周期只负责规划与结构动作。这是消除 89 分钟饥饿的治本项，复用 Phase 1 已拆出的 `enqueue()`。
3. **分片内存**：`send_chunk_request` 收 `bytes::Bytes`，去掉 `chunk.to_vec()` 副本。

### A3. 恢复语义（Phase 2）

| 项 | 改法 |
|---|---|
| `WaitingForNetwork` 无唤醒 | `next_retry_at` 兜底 `now + 60s`，纳入 `next_backoff_deadline_ms`；或让 `resume_waiting` 对"在线且已到期"的行在任意周期执行 |

| 8484 柬埔寨（569MB） | 11:16:43 | 11:23:33 | 6 分 50 秒 |

| 8483 KK园区（975MB） | 11:11:19 | 11:23:37 | 12 分 18 秒 |

同期日志显示：03:10:58 之后 **12 分半没有任何同步周期运行**（`auto-cloud-refresh` 每分钟一次的节奏中断），直到 11:23:23 应用崩溃重启、11:23:30 重新拉起，才在启动周期里把这批任务核验完。

#### A6.2 四个叠加原因

**① 核验不是连续调度，而是"蹭"特定周期**

`resume_verifying` 只在携带 `ONLINE_RECOVERY` 的周期里执行（`src/sync/engine/cycle.rs:412-435`），即 `startup-resume` / `network-recovery` / `backoff-deadline`。每 60 秒的 `auto-cloud-refresh` **不做核验**。今天全天只跑了 3 次 `backoff-deadline` 周期，其余全是 auto 周期——核验机会本来就不多。

**② 核验里内联执行重传，占死唯一的周期 owner**

```rust
// src/sync/task_runner/recovery.rs:326-328
// run_expected 会自行获取同一路径许可；确认未提交后才释放核验许可。
drop(activity);
self.run_expected(pending, true).await.map(Some)
```

核验一旦判定"未提交"，就在**同一个周期线程里同步重放整次上传**。1.3～2.6GB 的文件就是几十分钟；这段时间 `drain_cycle_requests_for` 的 owner 锁一直被占着，其它任务的核验、自动刷新、目录同步全部排队。这就是"一条卡住、全体停在正在确认结果"的直接原因。

**③ 每条核验本身也不便宜**

没有持久化 `remote_result_file_id` 时（收尾歧义路径不落 id），`verify_remote` 只能 `list_all(parent)` 逐页翻父目录找同名同大小候选（`src/sync/executor/transfer_operations.rs:565-607`）：

- 候选缺少 `createdTime` → 直接判 `Ambiguous`（"发现同名同大小资源但缺少创建时间"），60 秒后再来一遍；
- 候选带 64 位 `content_hash` → 触发本地整文件 SHA-256（`src/mount/file_hasher.rs:10`，64KB 缓冲、async 循环）；
- 失败退避 60 秒，最多 60 次 ≈ 1 小时才转 `Failed`。

实测单条核验约 25 秒（4 条约 98 秒），其中大头是多次网络往返，而不是哈希（本机 `openssl dgst -sha256` 1.9GB 仅 0.9 秒，说明现有哈希实现偏慢但非主因）。

**④ 反复"确认"的源头没修**

今天 11:11、11:14、11:16、11:22、11:24、11:27 仍在产生"收尾响应缺 `size`"的歧义（C1 未修）。每次上传完成都会掉进核验；每次核验失败又会触发一次重放，重放后再次歧义 —— 直到 `MAX_REPLAY_ROUNDS = 5` 才罢手。

#### A6.3 修复方案

| 编号 | 改动 | 效果 |
|---|---|---|
| A6-1 | **核验里的重放改为入队**：`NotCommitted` 分支不再 `run_expected(...).await`，改为 `enqueue + start_background_transfer`（复用 B1 的入队接口），核验函数立即返回 | 周期秒级释放，其它核验不再被一条大文件堵死 |
| A6-2 | **收尾即落远端 id**：只要收尾响应里有合法 `id`，先持久化 `remote_result_file_id`（即使 File 不完整），核验优先 `files.get(id)` | 核验从"翻父目录 + 猜"变成一次精确定点查询 |
| A6-3 | **缺 `createdTime` 不再升级为歧义**：能按 `id + name + size` 证明即可接受；确实需要时间窗时再查一次 `files.get` | 消除 60 秒 × 60 次的空转 |
| A6-4 | **哈希优化**：64KB → 1MB 缓冲、`spawn_blocking`、按 `(path, size, mtime)` 缓存结果 | 同一文件多轮核验不再重复整盘读取 |
| A6-5 | **核验独立调度**：新增轻量定时器（10～15 秒扫描到期 `VerifyingRemote`），不占 cycle owner；或至少让 `auto-cloud-refresh` 周期也执行核验 | 核验不再依赖 `backoff-deadline` 的稀缺机会 |
| A6-6 | **文案分阶段**：`VerifyingRemote` 在 UI 上拆成"等待核验（排队）/ 正在核验 / 等待重试（N 秒后）"，并在行内展示 `verify_attempt_count` 与下次重试时间 | 用户能区分"在跑"和"卡住" |

#### A6.4 验收

- 上传完成后 30 秒内完成结算（不含重传时间）；`VerifyingRemote` 平均停留 < 60 秒。
- 任一任务进入核验或重放时，`auto-cloud-refresh` 周期仍保持每分钟节奏（不中断）。
- 日志能区分三种核验去向：`核验命中 → 结算`、`核验未提交 → 已入队重放`、`核验仍歧义 → N 秒后重试`。



### B1. 重试：UI 不持锁、队列化、一键全重试（Phase 1，重点）

#### B1.1 设计原则

> **UI 上的"重试中"只表示"这一条请求正在提交"（毫秒级），不表示"任务正在执行"。**
> 任务是否在跑，一律以传输队列的权威状态为准。

由此推出三条硬约束：

1. 行级按钮的 loading 只绑本行，不得出现"任意一条在重试 → 全部禁用"。
2. 点击后立即把该行乐观置为"等待开始"，按钮随状态自然消失（`canRetryTransferTask` 只对 `FAILED` / `RESTART_REQUIRED` 为真）。
3. 后端命令必须在 100ms 内返回，任何耗时校验（稳定性检查 3～10 秒）移到后台。

#### B1.2 现状为什么"卡"

- 前端 `retryingId` 单值 + `:disabled="retryingId !== null"` + `onRetry` 早退（`TransferPopover.vue:63,144,325`）。
- 后端 `transfer_retry` 在命令路径同步跑 `prepare_retry` → `preflight` → `StabilityChecker::check`（固定 `sleep(3s)`，重试阶梯最多 ~13 秒）。
- 两者叠加：单击一次要 3～10 秒，且期间整列按钮全灰。

#### B1.3 后端合同改造

```rust
/// 单个重试请求的入队结果。
#[derive(Debug, Clone, Serialize, Type)]
pub enum RetryEnqueued {
    /// 本次请求已把任务推进到 Pending。
    Queued { task_id: i64 },
    /// 任务本来就在队列中（幂等），不视为错误。
    AlreadyQueued { task_id: i64 },
}

/// 一键重试全部失败项的汇总。
#[derive(Debug, Clone, Serialize, Type)]
pub struct RetryAllSummary {
    /// 本次新入队的任务数。
    pub queued: u32,
    /// 已在队列中而跳过的任务数。
    pub already_queued: u32,
    /// 不可重试而跳过（删除类任务、云端冲突）。
    pub skipped: u32,
    /// 校验失败的任务数（源文件已变化等）。
    pub rejected: u32,
}
```

命令：

| 命令 | 语义 | 返回 |
|---|---|---|
| `transfer_retry(task_id)` | 幂等入队；只做静态校验 + CAS，**不做后端前置校验** | `RetryEnqueued` |
| `sync_retry_failed()` | 遍历全部 `Failed`，逐个入队，立即返回汇总 | `RetryAllSummary` |

`prepare_retry` 拆分：

```rust
/// 把失败任务推进到 Pending（幂等）。只做静态校验，耗时校验交给后台。
pub async fn enqueue_retry(&self, task_id: i64) -> AppResult<RetryEnqueued> {
    let current = self.load(task_id)?;
    match current.state_kind().map_err(transition_error)? {
        // 已在队列：幂等返回，前端不必区分。
        TransferState::Pending | TransferState::Running | TransferState::VerifyingRemote => {
            return Ok(RetryEnqueued::AlreadyQueued { task_id });
        }
        TransferState::Failed | TransferState::RestartRequired => {}
        _ => return Err(AppError::generic("任务已结束，不可重试")),
    }
    // 静态校验只读本地元数据，微秒级；失败要持久化以便 UI 显示原因。
    if let Err(failure) = self.validate_static(&current) {
        self.persist_preflight_rejection(&current, failure.clone())?;
        return Err(AppError::generic(failure.message));
    }
    // 人工重试开启新一轮预算：accept_retry_after_preflight 内部会再复校一次静态合同，
    // 并把 attempt_count / verify_attempt_count 归零。
    let pending = self.accept_retry_after_preflight(task_id, current.state_revision)?;
    Ok(RetryEnqueued::Queued { task_id: pending.id })
}
```

一键重试复用同一入口，按 `created_at` 升序遍历，跳过同名冲突（需要用户三选一）与删除类任务：

```rust
/// 把全部失败项加入队列并立即返回汇总；不等待任何任务执行。
pub async fn enqueue_all_failed(&self) -> AppResult<RetryAllSummary> {
    let mut summary = RetryAllSummary::default();
    let mut tasks = self.list_states(&[TransferState::Failed, TransferState::RestartRequired])?;
    tasks.sort_by_key(|task| task.created_at);
    for task in tasks {
        // 同名冲突必须由用户选择处理方式（覆盖/保留两者），不能自动重放。
        let is_name_conflict = task.error_kind_typed().ok().flatten()
            == Some(TransferErrorKind::NameConflict);
        if is_name_conflict {
            summary.skipped += 1;
            continue;
        }
        match self.enqueue_retry(task.id).await {
            Ok(RetryEnqueued::Queued { .. }) => summary.queued += 1,
            Ok(RetryEnqueued::AlreadyQueued { .. }) => summary.already_queued += 1,
            Err(_) => summary.rejected += 1,
        }
    }
    Ok(summary)
}
```

执行侧改动：`run_prepared_in_background` 内部改调 `run_expected(task, true)`，让 `operations.preflight`（稳定性窗口）在后台跑；失败时仍走 `persist_preflight_rejection` 并广播状态。

#### B1.5 调度与并发

- 入队后由 `TransferScheduler` 统一调度：内存 `HashSet<task_id>` 去重 + `tokio::spawn` + `execution_slots` 信号量（= `concurrency`）。
- 同一任务重复入队由信号量外的去重集合与数据库 CAS 双重保证幂等。
- 应用退出后 `Pending` 行由启动恢复（`recover_startup`）继续，不丢用户意图。

#### B1.6 边界与例外

| 场景 | 行为 |

| 删除类任务 | 前端 `canRetryTransferTask` 已限制，不显示重试 |

| 重复点击同一条 | 幂等返回 `AlreadyQueued`，不报错、不重复执行 |

#### B1.7 验收

- 连续快速点击 5 条失败项：5 条立即变「等待开始」，按钮互不影响。
- 一键重试 30 条：命令返回 < 100ms，队列立即显示 30 条「等待开始」，随后按并发 6 执行。
- 同一条重复点击：无报错，队列里仍只有一条。
- 界面上不存在任何跨行的 disabled/loading 关联。

### B6. 托盘菜单：刷新时不能把菜单关掉（Phase 1）

#### 现象

传输进行中，托盘菜单里会展示「正在传输」段。但菜单每隔几秒就会自己关闭，用户必须反复重开；有时刚点开就消失，根本来不及点「显示主窗口」。

#### 根因

1. `refresh_menu` 每次都用 `build_menu` **重建整个 `Menu`**，再 `tray.set_menu(Some(menu))`（`src/platform/tray.rs:297`）。macOS 上替换 `NSStatusItem.menu` 会结束当前菜单追踪，**已展开的菜单被立即关闭**——代码注释里也承认「过频重建会让已展开的菜单闪烁消失」。
2. 触发源有两个（`src/runtime.rs:798`、`:843`）：`transfer_update`（进度，约 0.5～1 秒一次）与 `sync_state`（每次状态发布）。它们都会调用 `refresh_menu`。
3. 节流粒度不对：`MENU_REBUILD_INTERVAL_MS = 5000`，所以**传输期间每 5 秒重建一次**；而且重建签名 `transfer_signature` 里含 `transferred`/`total_size`（`tray.rs:261-271`），进度一变签名必变，节流窗口一过就必然重建。
4. 任务结束/开始时 `has_active` 翻转，走的是**不节流**分支，立即再重建一次。

结论：这不是偶发，而是「按进度刷新 + 整菜单替换」的必然结果。

#### 方案

**B6-1 结构稳定，只改文本（主方案）**

托盘菜单在启动时建成固定结构，之后只调用 `MenuItem::set_text` 更新文字，**不再 `set_menu`**：

```
PetalLink - 华为云盘桌面客户端开源版     (disabled)
──────────────
显示主窗口
正在上传 2 项 · 45%                      (disabled，文本原地更新)
──────────────
退出 PetalLink
```

- `set_text` 只改 `NSMenuItem.title`，不替换 `NSMenu`，因此**不会关闭已展开的菜单**；
- 百分比只是"打开时看到的快照"，不追求菜单开着时实时跳动；
- 需要保留 `MenuItem` 句柄（managed state）或用 `Menu::get(id)` 取回再更新；实现时需确认 `MenuItem<Wry>` 是否 `Send + Sync`，否则用 `Menu::get`。
- 若产品坚持保留"逐条任务"：改为固定 3 个槽位 + 超出显示「还有 N 项，在应用内查看」，同样只 `set_text`。

**B6-2 签名只反映结构**

`transfer_signature` 去掉 `transferred`/`total_size`，只保留 `(count, id 集合, state 集合)`。进度不再触发结构重建。

**B6-3 结构变化也要 debounce**

即使必须重建（0→N、N→0、槽位超限），也要合并短时间内的多次变化，静默 1.5～2 秒后再重建，避免"刚点开就赶上重建"。现有 5 秒定时节流可退化为结构重建的最小间隔（如 30 秒）。

**B6-4 减少无谓查询**

`refresh_menu` 现在先 `load_active_transfers()`（一次 DB 查询）再做签名/节流判断，传输期间约 2Hz 落库查询。可改为由事件携带活跃计数，或把查询收敛到结构重建前。

**B6-5（可选，P2）菜单展开期间冻结**

用 macOS `NSMenuDelegate` 的 `menuWillOpen/didClose` 记录展开态，展开期间一律不重建。需要 objc2/私有 API，成本较高，先不做硬依赖——B6-1/2/3 已能消除 99% 的关闭。

#### 附带收益

- 重建次数从「传输期间每 5 秒一次」降到「每批任务几次」，`muda` 图标渲染 panic（D32）的暴露面同步下降。
- 菜单打开时不再有内容抖动，符合 macOS 原生工具的交互预期。

#### 验收

- 传输进行中打开托盘菜单，**保持 60 秒不被关闭**；
- 一批 30 个文件的传输期间，托盘菜单结构重建 ≤ 4 次（开始、结束、槽位超限）；
- 重新打开菜单时文字是最新的（百分比允许滞后）；
- 无传输时菜单仍是三段式，不出现空行。

### B7. 第二轮 UI 优化清单（U01–U18）

前提：**不改变任何同步判据**。所有 UI 改动只能提升"可见性、可达性、可撤销性、反馈质量"，不得让界面自己发明同步状态。

1. **UI 不发明状态**：同步态只能来自 `transfer_queue` / `sync_items` 与事件；禁止用"本地文件存在 + 大小一致"推测已同步。

## 5. 统一任务队列（两条主线的共同基座）

### 5.0 通道模型：控制面与数据面必须分开

#### 现状：一个通道承载三类工作

```
run_sync_cycle(trigger) ──┐
auto-cloud-refresh ───────┤
backoff-deadline ─────────┼──> drain_cycle_requests_for()
startup-resume ───────────┤      └─ _owner = cycle.lock_owner()        ← 全局串行，持到周期结束
manual-refresh ───────────┘         ├─ changes 追平 / 云树刷新           （控制面）
                                    ├─ planner.plan()                   （控制面）
                                    ├─ execute_actions_ordered()        （数据面，`await` 到底）
                                    │    └─ enqueue_and_run() → 上传 1～2GB
                                    └─ resume_verifying()               （控制面）
                                         └─ NotCommitted → run_expected().await
                                              ↑ 核验里又跑了一次数据面（recovery.rs:328）
```

三类工作的天然频率差三个数量级，却被放进同一个串行通道：

| 工作 | 单次耗时 | 期望频率 | 真正需要的互斥 |
|---|---|---|---|
| changes 追平 / 规划 / 结构结算 | 数十毫秒 | 每分钟 | 基线提交串行（短临界区） |
| 核验（读证明 + 行级 CAS） | 100ms～数秒 | 10～60 秒 | 行级 CAS，无需全局 |
| 传输（上传/下载） | 分钟～小时 | 按用户意愿 | 并发槽 + 路径租约（已有） |

**短任务的实际执行频率由最长任务决定** —— 这就是"确认要确认十分钟"的结构性原因，不是某一行代码写错。

#### 为什么当初会这样（合理的历史约束）

代码注释给出了三个真实约束，它们都成立：

1. `Changes` 必须追平后再规划，否则会用旧云树把新基线反向重键（`cycle.rs:319`）；
2. 结构动作（创建目录/改名/删除）必须在结算前写回基线，否则下一轮规划会重复执行；
3. 路径恢复必须先于核验（`cycle.rs:399`：「核验不能提前到这里之前，否则 Changes 尚未可见时，新基线可能被旧云树反向重键」）。

问题不在意图，而在**粒度**：把"基线提交的临界区"放大成了"整个数据面的生命周期"。

#### 目标模型：三条通道 + 两个既有原语 + 一条排序合同

| 通道 | 承载 | 互斥方式 | 是否占用 cycle owner |
|---|---|---|---|
| **规划通道**（控制面） | changes 追平、云树刷新、planner、结构动作结算、checkpoint | 全局串行，**只在快照→提交期间** | 是（但秒级） |
| **执行通道**（数据面） | 上传/下载 | `execution_slots` 信号量 + `ActivityGate` 路径租约 | 否 |
| **核验通道**（探针） | 列目录 / `files.get`、任务行 CAS、判定"已提交/未提交/仍歧义" | 只读 + 行级 CAS；需要重放时只**投递**回执行通道 | 否 |

排序合同（保证正确性，不靠大锁）：

1. 规划只读快照（`cloud_tree_revision` + 本地扫描 + DB 快照），产出 intent，**不等待执行结果**。
2. 执行按 intent 落库并异步运行；结算时把结果写回基线（`cloud_entry_insert` + `sync_items`），并携带产生该 intent 时的 revision。
3. 规划周期开始时**先吸收上一批结算结果**（settlement inbox，有界），再规划；计划前已有的在途意图由 `filter_active_transfer_actions` 隔离。
4. 结构动作与传输在同一路径上的互斥由 `ActivityGate` 路径租约保证（已存在），不再依赖全局 owner。
5. 核验永远不执行上传；判定需要重放时调用 `enqueue`（B1 的入队接口）。

**可行性已被现有代码证明**：手动重试走 `run_prepared_in_background`（`src/sync/engine/retry.rs:36`），它在周期之外执行传输，并通过 `cloud_entry_insert` 直接更新基线。规划驱动的路径只是没有复用这套机制。

#### 迁移步骤（Phase 2，拆成 16a/16b/16c 三步，可独立回滚）

| 步骤 | 内容 | 验收 |
|---|---|---|
| 16a | 核验通道独立调度：新增 10～15 秒定时核验器，`resume_verifying` 从周期移除（重放入队已在 Phase 1 完成） | 核验不再被周期阻塞；`VerifyingRemote` 停留 < 60 秒 |
| 16b | 执行通道独立：`execute_transfer_action` 改为 `enqueue + start_background_transfer`，周期不再 `await` 传输；新增 settlement inbox 在周期开头吸收结果 | 单周期 p95 < 30 秒；30GB 批量上传期间 auto 周期不断档 |
| 16c | 规划通道瘦身：结构动作按路径租约并行（可选）、`scan_local` 增量补丁 | 空闲 CPU 下降，周期更短 |

#### 不变量（迁移期间必须保持）

- 任一时刻同一路径只有一个"会改远端"的意图在跑（TaskRunner CAS + `ActivityGate`）。
- 云端基线只会被"已结算"的结果更新；未结算的意图不写基线。
- 结算结果晚到不会导致重复上传/删除：计划前先吸收 inbox，并隔离在途意图。
- 结构动作永远先于依赖它的传输（建目录 → 上传），由 planner 的动作顺序与路径租约共同保证。


### 5.1 分层

| 层 | 实体 | 职责 | 持久化 |
|---|---|---|---|
| 编排 | `FolderSyncJob` | 一次「双端对齐」请求：BFS、建目录、计算差异、**入队传输任务** | 新表 `folder_sync_jobs` |
| 执行 | `TransferTask` | 单个文件的上传/下载 | `transfer_queue` |
| 基线 | `SyncItem` | 已对齐的文件事实 | `sync_items` |

### 5.2 数据模型（schemaVersion 7）

```sql
CREATE TABLE IF NOT EXISTS folder_sync_jobs (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    folder_id      TEXT    NOT NULL,          -- 云端目录 ID
    rel_path       TEXT    NOT NULL,          -- 挂载根内相对路径
    state          INTEGER NOT NULL DEFAULT 0,-- 0 queued, 1 planning, 2 completed, 3 failed, 4 canceled
    planned_total  INTEGER NOT NULL DEFAULT 0,
    enqueued       INTEGER NOT NULL DEFAULT 0,
    error_message  TEXT,
    created_at     INTEGER NOT NULL,
    started_at     INTEGER,
    finished_at    INTEGER,
    state_revision INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX IF NOT EXISTS idx_folder_sync_jobs_state
    ON folder_sync_jobs(state, created_at);

-- 同一目录同一路径只允许一个未完成作业（幂等去重）
CREATE UNIQUE INDEX IF NOT EXISTS idx_folder_sync_jobs_active
    ON folder_sync_jobs(folder_id, rel_path) WHERE state IN (0, 1);
```

迁移：`SCHEMA_VERSION` 6 → 7，`upgrade_to_v7` 只加表与索引。

### 5.3 执行模型

```
FolderSyncWorker（新增 src/sync/engine/folder_queue.rs）
  loop:
    job = 取最老 queued（无则等 Notify / 2s 超时）
    等 try_begin_folder_sync_guard()（false 则 500ms 后重试，作业保持 queued，不报错）
    置 planning → BFS → 建目录 → 计算差异 → 逐条 enqueue 传输任务
    释放 guard（仅此时）→ 置 completed → 对入队任务逐个 schedule
```

配套：

- `TaskRunner::enqueue(task)`：把 `enqueue_and_run` 拆成"准入 + 落库"与"执行"两段，准入逻辑（去重、重规划、Failed 屏障）完全复用。
- `SyncEngine::start_background_transfer(task_id)`：复用 `run_prepared_in_background` 的后台执行 + 成功回填 `cloud_entry_insert` + 失败触发 replan。
- 并发由 `execution_slots` 信号量统一约束。

### 5.4 互斥收窄

| 锁 | 现状 | 变更后 |
|---|---|---|
| `folder_syncing` | 整个目录同步期间持有（含全部传输） | 仅 `planning` 阶段持有 |
| `syncing` | 目录同步准入时也要判空 | 仍判空，但 worker **等待**而非失败，窗口从小时级降到秒级 |
| 周期 | `folder_syncing` 为 true 时全部让路 | 只在规划窗口让路，传输阶段周期可继续 |

## 6. coding-rules 合规要求

本节为本次迭代的**强制验收项**，review 时逐条核对。

### 6.1 Vue / TypeScript

- `<script setup lang="ts">` 内顺序固定：`import` → `const/let/ref/computed` → `defineProps/defineEmits` → 生命周期 → `defineExpose` → `watch` → `function`。
- 所有 `const/let` 必须有 `//` 单行注释；多行声明前后空行，单行声明不空行。
- 函数用 `function` 声明，JSDoc 必须换行（`/**` 后换行）；`watch` 用紧凑写法。
- 回调一律箭头函数；异步一律 `async/await + try/catch`，禁止 `.then/.catch` 链。
- 魔法字符串抽为 `UPPER_SNAKE_CASE` 常量（如新增的 `RETRY_STATE_LABEL`）。
- 模板内禁止带单位的 `style`；颜色等简单样式允许；带单位样式放 `<style scoped>`。
- 新组件必须复用 `app/components/mate/`，不得自造按钮/弹层。

### 6.2 Rust

- 文件、模块职责用 `//!`；`fn`/`struct`/`enum`/`const` 等命名声明用 `///`。
- 多阶段函数（校验、IO、状态迁移、发布）在对应代码前用 `//` 标明阶段；超过约 15 行的连续业务代码要分段。
- 锁边界、重试、恢复、HTTP 写操作必须说明成功判定与禁止事项（本方案 D1 的修复即典型）。
- 单个生产文件不超过 1000 行；新逻辑优先拆子模块（`folder_queue.rs` 独立成模块）。
- 门面文件只保留声明与编排，读写/解析/持久化下沉。
- 错误信息不回显底层细节，稳定文案走 `AppError`。

### 6.3 测试

- Rust 集成测试统一放 `tests/*_test.rs`；确实依赖私有实现的纯函数（如协议解析）允许 `#[cfg(test)] mod tests` 内联。
- 前端测试统一放 `app/tests/*.test.ts`，引用被测模块用 `@/` 别名。
- 新增测试文件命名见 §9。

### 6.4 文档同步

- 行为、命令、状态机、配置变化必须同步更新 `README.md`、`docs/概要设计文档.md` 与 `docs/release-notes/v1.2.0.md`。
- 本文档在实施过程中如与实现偏离，以源码为准并回写本节。

### 6.5 UI 权威状态原则（新增）

- 前端所有同步状态必须来自 `transfer_queue` / `sync_items` / 事件；禁止用本地文件存在性、大小、时间戳推测「已同步」。
- 乐观更新只允许用于「用户刚发起的操作」，且必须在事件回填后以权威状态为准；失败要回滚。
- 批量操作只能调用既有入队入口，不得绕过去重、CAS 与路径闸门。

### 6.6 Git

- **不自动提交**；改动完成后列出文件清单与验证结果，由用户决定是否提交。
- commit message 使用中文，仅包含本次改动。

## 10. 风险与回滚

| 风险 | 影响 | 缓解 |

### 偏差与实现说明

- **A6-2（收尾即落远端 id）由 C1 覆盖**：C1 让「缺 `size` 但 id 与名称齐全」的收尾直接按任务快照补全并返回完整 `DriveFile`，id 因此照常进入 `execute` 的 `edited_time.is_none()` 分支并落到 `remote_result_file_id`。再单独把「id 存在但身份无法证明」的残缺 File 透传上来会引入「用未证明的 id 参与核验」风险，故未按原方案改动函数签名。
- **`tests/sync_folder_queue_test.rs` 改为内联测试**：`data` 模块对 crate 外不可见，作业仓储无法通过公开合同覆盖；按 coding-rules §4「确实依赖私有实现的核心测试允许保留在 `src/` 内」放入 `data/repository/folder_sync_jobs.rs` 的 `#[cfg(test)] mod tests`。
- **目录同步不再复用 `FolderSyncProgressEvent`**：该事件从来没有消费方；改由 `folder_sync_jobs_changed` 触发前端整表重载，作业本身即进度载体。
- **`prepare_retry` 保留**：自动恢复周期（`CycleRequest::RETRY`）仍走带后端前置校验的同步路径，避免一次自动重试把稳定性窗口挪出周期；用户点击路径才走 `enqueue_retry`。

用户明确要求杜绝「本地不可见 → 删云端唯一副本」。该方向一旦误判就是**用户数据不可恢复的丢失**，
因此新增四道硬闸门，任何一道不通过都只降级为 Skip（安全方向）。

| 闸门 | 位置 | 规则 |
|---|---|---|
| 1. 挂载缺失 | `engine/reconciliation.rs::guard_cloud_deletes` | `mount_dir` 未就绪 → 拒绝全部云端删除（无法本地核验就绝不盲删） |
| 2. 空扫描熔断 | 同上 + `cloud_delete_gate` | `local_len == 0 && db_len > 0` → 整批拒绝。这是「卷未挂载 / 目录被清空 / 权限变化」的典型形态，**用户确认也不放行** |
| 3. 批量阈值 + 显式确认 | 同上 + `MASS_DELETE_CONFIRM_THRESHOLD = 100`、`MASS_DELETE_RATIO_MIN_ENTRIES = 10` | 单轮波及条目满足任一条件且未确认 → 整批拦下：①≥100 条（绝对爆炸半径，目录按子树展开计入）；②≥10 条且 ≥ 基线总量的一半（覆盖「目录被清空但有残留」）。状态里给出 `blocked_cloud_deletes`，前端「已阻止 N 项云端删除」二次确认后才放行 |
| 4. 逐条 + 执行前复核 | `validate_delete_from_cloud`、`executor/actions.rs::do_delete_from_cloud` | 删除前 `symlink_metadata` 复核：本地仍存在（**含占位符**）或无法证明缺失 → 拒绝；执行侧在下发请求前再做一次同样语义的复核，覆盖「规划→执行」窗口 |

配套：`sync_approve_mass_delete` 命令（一次性令牌）、`SyncGlobalState.blocked_cloud_deletes` 字段、
状态条「已阻止 N 项云端删除」chip + 二次确认弹窗。

**关键行为变化**：占位符以前被当作「本地无内容、可以删云端」，现在改为「本地仍存在、拒绝删除」。
理由：占位符意味着该条目的内容只存在于云端，删掉云端等于删掉唯一副本；真正在 Finder 里删除占位符后，
路径根本不存在，删除仍会正常放行。

### 本批未完成（继续排在后续批次）

Phase 1 的 16 项已全部落地；Phase 2 已完成 16a、17（D5/D6/D8/D9/D10/D11）、18（D7/D16/D17）与 19 的前两项（D13/D14）。

**方案规划项已全部处理**，仅 1 个子项按「不牺牲正确性」原则保留现状：

| 项 | 结论 | 原因 |
|---|---|---|
| 3-D26 本地增量扫描（唯一保留项） | 保留每周期全量扫描 | 增量扫描依赖「本地树缓存 + watcher 失效」。危险方向是「缓存说本地不存在、实际存在」——那会让 planner 生成 `DeleteFromCloud`，直接删用户的云端文件；watcher 溢出/漏事件时就会走到这一步。当前 27k 文件全量扫描在阻塞线程池执行，实测是百毫秒级，收益不抵数据风险。本轮已把周期快照的三次全量深拷贝降到一次（`local`/`cloud` 直接移入）。若后续要做，必须同时实现：启动全量预热、watcher 溢出强制全量、以及「缓存缺失即降级为全量」的熔断。 |

19-D15 的最终实现没有改用 `queryParam` 搜索（索引延迟会造成重复目录），而是**复用父目录的权威遍历结果**：同一次目录同步作业内，同一父目录 5 秒内只翻页一次，且遍历失败一律跳过创建。

16c 的「结构动作按路径租约并行」实际已由 `execute_actions_ordered` 的并发执行 + 路径租约满足（目录创建必须按深度串行是正确性要求）。

- 唯一与原方案不同的一处取舍：`config_save_sort` 走独立命令而不是整份 `config_save`，避免每次点表头都读改写整份配置、与设置页保存互相踩踏；该命令只改排序字段，不触发引擎重建。
