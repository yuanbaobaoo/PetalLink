# 同名冲突与解析兼容根治方案（v1.1.10）

日期：2026-09-16
关联：`2026-09-16-上传死循环与卡顿修复方案.md`（v1.1.9）遗留事项 F3B

## 背景

v1.1.9 修复「核验未提交 → 重放」无限环路后，两个上传任务呈现「100% 但一直确认结果」，
随后落入「需要重新检查：目标目录已存在同名远端文件，拒绝重复创建」，点重新检查无限循环、记录永不消失。

根因链条：

1. 华为 finalize/读接口响应 schema 漂移：`size` 返回字符串（如 `"12345"`），
   `DriveFile::from_json` 只接受数字，静默解析为 0 → 收尾校验失败 → 判定远端写入歧义。
   （写响应路径 `parse_written_drive_file` 无 size 校验，静默吞掉；
   读路径 `parse_drive_file_strict`/changes 严格校验则直接整页/整条报错。）
2. 远端核验的调和逻辑（按 ID 或名称+大小+窗口+哈希采纳远端文件）存在两个断点：
   - `replan_task` 清空 `remote_result_file_id`，含歧义结果的任务永远无法升回核验态按 ID 精确核验；
   - size 解析为 0 使大小硬比对把真实文件滤掉。
3. Create 前的同名碰撞检查只比文件名，同名即拒绝 → RestartRequired；该路径不消耗重试预算，
   永不转终态 → 「重试 → 重规划 → 撞同名 → 再重启」死循环，且没有任何用户出口（跳过/覆盖/取消）。

## 修复内容

### A. 解析层根治（F3B）

- `drive/models.rs`：`DriveFile::from_json` 的 size 改用 `tolerant_parse_int`（接受数字/字符串）；
  无法解析时回退 0 并落 debug 日志。`to_json` 始终写出 size（0 字节文件与未知大小可区分）。
- `drive/files_api/response.rs`：`validate_optional_nonnegative_i64` 接受字符串型非负整数。
- `drive/changes_api.rs`：change 事件 size 校验接受整数字符串。
- `drive/download_api.rs` 的 `parse_u64` 原本已容忍字符串，无需改动。

### B. 碰撞检查升级为内容一致性判定

- `executor/transfer_operations.rs` 新增纯函数 `decide_name_collision`：
  同名候选 size 必须等于上传源大小；远端带可比 SHA-256（64 位 hex）时以哈希裁决
  （一致即采纳，不依赖创建窗口；不一致即排除）；哈希不可比时回退创建时间窗口
  （任务创建时间 -120s ~ +30 天，与 `verify_remote` 无 ID 分支同语义）。
  唯一候选 → Adopt；零或多候选 → Conflict。
- execute 的 Create 分支：Adopt 时先落 fileId xattr（失败则 RestartRequired 保留重试），
  再返回 `TaskExecutionOutcome{cloud_file, Completed}` 走现有 `validate_success_outcome`/`settle_success` 结算；
  Conflict 时返回新的 `TaskExecutionError::NameConflict`。
- 新增 `TransferErrorKind::NameConflict = 12`（持久化枚举，稳定性测试已登记）；
  映射为 state=RestartRequired + error_kind=NameConflict +
  文案「目标目录已存在同名远端文件且内容不一致，请选择处理方式」。
- `admission.rs` replan 不再清空 `remote_result_file_id`（`ColumnPatch::Keep`），
  使 `promote_ambiguous_restarts` 能把含歧义结果的任务升回核验态按 ID 精确核验。
- `verify_remote` Create 按 ID 核验时 name/size 不匹配改判 NotCommitted（原 Ambiguous 要约 1 小时才收敛），
  经重放快速进入碰撞检查收敛。

### C. 用户三操作（不丢文件，除非用户故意覆盖）

- 后端 IPC（`commands/transfer.rs`，bindings 已重新生成）：
  - `transfer_overwrite_remote`：守卫（RestartRequired+NameConflict、本地源快照未变）→
    远端同名文件改名为「原名 (云端副本 YYYY-MM-DD HH-mm-ss)」（`conflict.rs` 新增
    `dedupe_cloud_copy_name`，按远端同级去重）→ 任务重置 Pending 后台重放。
    零下载流量、不限大小、任何一步失败任务保持原状且旧版已成副本。
  - `transfer_keep_both`：本地文件改名为「原名 (本地副本 …)」（复用 `dedupe_copy_path`，
    清除残留旧 fileId xattr）→ 任务取消 → 触发重扫描，副本作为新文件自然上传。云端原文件不动。
  - `transfer_cancel`：RestartRequired/Failed → Canceled（「用户已取消该任务」）。
- 引擎层 `engine/conflict_actions.rs` 承载三个操作；`retry.rs` 抽出
  `run_prepared_in_background` 供重试与冲突重放共用。
- TaskRunner 新增 `user_actions.rs`：`load_name_conflict_task` / `requeue_name_conflict_task`
  （计数归零，与人工重试同语义）/ `cancel_user_task`（CAS 迁移）。
- 前端：`api/transfer.ts` 新增 `isNameConflictTask`/`canCancelTransferTask`；
  store 新增 `overwriteRemote`/`keepBoth`/`cancel`；`TransferPopover.vue` 对可取消任务行
  渲染「更多操作」菜单（同名冲突三项，其余仅取消），三项操作均 `confirmDialog` 二次确认；
  同名冲突任务不再显示「重新检查」重试按钮（重试只会回到同一决策态）。

### D. 释放空间弹窗

- `FileListView.vue`：列表项由文件名改为相对路径（`FreeableItem.relPath`，如 `a/b/c.txt`），
  弹窗宽度 420 → 640，长路径不截断、整表横向滚动。

## 现有两条滞留任务的自愈路径

升级后点一次「重新检查」→ 重规划 → execute 碰撞检查：远端带可比哈希则自动采纳结算成功；
否则因 replan 刷新 `created_at` 使创建窗口不命中而进入 NameConflict，用户在菜单里点一次
（覆盖/保留两者/取消）即了结。不再无限循环。

## 已知边界

- 取消任务后，该路径在 planner 视角为「本地有+云端有+无基线」的 Skip 态，
  文件保持未同步直到任一端出现新变化——取消即用户接管，属预期。
- 覆盖操作在「改名远端旧版 → 新上传完成」之间，云端短暂没有以原名存在的文件
  （旧版在副本名下），可接受且不丢数据。
- 保留两者会改动用户本地文件名（改名为本地副本），确认弹窗已明确告知。
- 若华为响应还有其他未见的漂移形态，`log_incomplete_final_body` 取证日志保留，可继续补兼容。

## 追加修复（v1.1.10 发布后复盘，随 v1.1.11 发出）

v1.1.10 上线后两条存量滞留记录仍显示旧文案且无法清除。根因：RestartRequired 的
「重新检查」走 retry-replan 周期，依赖 planner 重新产生上传意图；但同名碰撞场景下
planner 看到「本地有 + 云端有 + 无基线」只产出 Skip（`planner.rs` 首次记录兜底分支），
replan 永远等不到替代意图，任务从未真正重新执行——v1.1.10 的碰撞检查升级根本不会被触发。

修复：

- `admission.rs` `prepare_retry` / `accept_retry_after_preflight` 直接接受 RestartRequired
  （此前仅 Failed）：重试即重跑，execute 的碰撞检查基于远端实时状态收敛（采纳或 NameConflict）；
  兼容同步状态改为无条件拨回 SYNCING（RestartRequired 来源的行未必处于 FAILED）。
- 前端：普通 RestartRequired 行在重试按钮旁同时渲染「更多操作」菜单（含取消），
  滞留记录不依赖重试也有出口。
- 测试：`sync_task_name_conflict_test.rs` 新增 `restart_required_task_can_retry_directly`；
  `transfer-state-ui.test.ts` 更新菜单渲染断言。
